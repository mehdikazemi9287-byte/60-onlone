# مرحله‌ی ۰ — روشن کردن پرداخت واقعی با درگاه سپهر

این کارها روی سرور انجام می‌شوند و از داخل ریپو قابل انجام نیستند.

## ۱. از شرکت پرداخت الکترونیک سپهر بگیرید

- **شماره‌ی ترمینال (Terminal ID)** درگاه اینترنتی.
- ثبت **آی‌پی سرور** در پنل پذیرنده. بدون آن، مرحله‌ی تأیید (Advice) رد می‌شود.
- ثبت دامنه‌ی `60online.ir` به‌عنوان آدرس بازگشت.
- از سرور، پورت‌های ۸۰۸۰ و ۸۰۸۱ مقصد `sepehr.shaparak.ir` باید باز باشند.

## ۲. متغیرهای محیطی بک‌اند

```
PAYMENT_PROVIDER=sepehr
SEPEHR_TERMINAL_ID=<شماره‌ی ترمینال>
PUBLIC_BASE_URL=https://60online.ir
STOREFRONT_SALES_ENABLED=1
CURRENCY=IRR
CURRENCY_EXPONENT=0
```

- اگر `SEPEHR_TERMINAL_ID` خالی باشد یا `PUBLIC_BASE_URL` با `https://` شروع نشود، بک‌اند اصلاً بالا نمی‌آید.
- مبلغ‌ها به ریال به بانک فرستاده می‌شوند.

## ۳. مسیر nginx

بانک مرورگر مشتری را به این آدرس برمی‌گرداند (POST فرم):

```
https://60online.ir/api/v1/payments/sepehr/callback
```

قانون فعلی `/api/` → بک‌اند آن را پوشش می‌دهد. چیزی اضافه لازم نیست، مگر لایه‌ای جلوی `/api/` درخواست‌های فرم را رد کند.

## ۴. آزمون قبل از باز کردن برای مشتری

1. یک کالای واقعی با قیمت و موجودی تأییدشده، و یک خرید با کمترین مبلغ ممکن.
2. لغو روی صفحه‌ی بانک → برگشت به `/checkout?payment=failed` و آزاد شدن موجودی.
3. پرداخت موفق → برگشت به `/orders/ORD-…?payment=success` و سفارش با وضعیت «پرداخت‌شده».
4. در پنل سپهر، تراکنش موفق «تأییدشده» باشد و تراکنش لغوشده برگشت خورده باشد.

## رفتار سیستم

| وضعیت | نتیجه |
| --- | --- |
| بانک توکن نمی‌دهد | پولی کسر نمی‌شود، موجودی آزاد می‌شود، پیام «درگاه در دسترس نیست» |
| مشتری روی صفحه‌ی بانک لغو می‌کند | سفارش ثبت نمی‌شود، موجودی و اعتبار آزاد می‌شود |
| مبلغ برگشتی با مبلغ سفارش یکی نیست | تأیید نمی‌شود و درخواست برگشت پول (Rollback) فرستاده می‌شود |
| تأیید (Advice) رد می‌شود | سفارش ثبت نمی‌شود و Rollback فرستاده می‌شود |
| سرور به Advice نمی‌رسد | سفارش ثبت نمی‌شود؛ بانکِ تأییدنشده پول را خودش برمی‌گرداند |
| بازگشت از بانک بعد از ۱۵ دقیقه و آزاد شدن موجودی | Rollback فرستاده می‌شود و سفارش ثبت نمی‌شود |
| بازگشت تکراری از بانک | همان سفارش قبلی نشان داده می‌شود و سفارش دوم ساخته نمی‌شود |

## ۵. آزادسازی پرداخت‌های رهاشده

اگر مشتری صفحه‌ی بانک را ببندد، موجودی و اعتبارش ۳۰ دقیقه رزرو می‌ماند و بعد آزاد می‌شود. هر بار که مشتری دیگری پرداخت را شروع کند، این آزادسازی خودبه‌خود انجام می‌شود. برای اینکه بدون خرید جدید هم انجام شود، این را در cron سرور بگذارید:

```
*/5 * * * * docker exec <نام کانتینر بک‌اند> python -m scripts.release_abandoned_payments
```

## هنوز انجام نشده

- تطبیق دوره‌ای با گزارش تراکنش‌های بانک (برای پرداخت‌هایی که بانک موفق ثبت کرده ولی بازگشت مشتری به سایت نرسیده). بانک این‌ها را چون تأیید نشده‌اند خودش برمی‌گرداند، ولی گزارش‌گیری‌اش هنوز ساخته نشده.
- اجرای خود برنامه روی PostgreSQL. مایگریشن‌ها کامل و روی PostgreSQL 16 اجرا شده‌اند، ولی کوئری‌های برنامه هنوز روی PostgreSQL تست نشده‌اند. تا آن موقع، پروداکشن روی SQLite می‌ماند.
